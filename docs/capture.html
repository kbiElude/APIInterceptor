API Interceptor Overview Capture Components Building

Capture

Every call a program makes to the graphics API is seen and written down with its data, in a workload file that another program can read.

What happens to one call

Data chunks

DataChunkStore keeps the chunks. A chunk is registered when a call is made and given a number which is never used again. The store holds only the chunks from the oldest one that is neither taken nor released, so it does not grow while the program runs. A consumer takes a chunk once (take_data_chunk, or take_data_chunks for a run of them); taking moves the contents out.

Callbacks and the gate

CallbackRegistry holds the pre and post callbacks of each function (registered at start-up, never changed after). ApiCallGate lets the dumper hold other threads back from entering intercepted calls while it cuts a segment of the workload. All three are process-wide objects that are never destroyed, since hooks can still run while the process shuts down; the free functions in Common/callbacks.h forward to them.

Calls the interceptor makes itself

A program that builds on the interceptor (one that changes the calls, or plays them back) has to call the API too. Those calls go through OwnCallScope, which keeps the hooks from recording them as the program's.

The tools

ToolUse
APIDumperStarts a program with APIDumperDLL injected; the DLL writes the workload.
APIDumpPrinterPrints a workload as text, verbosely: every input and result; [out:] marks an argument the call changed by reference. --frame reads the file from the segment of the first frame, with the data chunks of the segments before it left out (the names of the objects are given by the order of their creation, so those calls are still read), by the index that --index makes: on a capture of 30,000 frames and 42 million calls the index is made in 7 seconds and is 8 KB, and printing frames near the end takes 12 seconds instead of 30. --verify reads a workload and says what a replay of it would fail on, without replaying it: the calls of functions that the replay has no code for (with the first call and frame of each), the functions that it leaves out on purpose, and references to data chunks that are not in the file; it exits with 1 if a replay would fail. It asks the executors of the replay engine, the same ones that decide when a call is replayed, so it cannot drift from them. --unreplayed-functions needs no workload and lists the functions that are recorded and cannot be replayed.
ReplayPlayerPlays a workload again in a window, with the replay engine, without the program.

The replay engine

ReplayEngineCore (a static library; ReplayEngineDLL is a thin shell around it) reads calls from a workload (in segments if it is large; see WorkloadReader) and executes each through an ICallExecutor, one after the other. Observers (IReplayObserver) hear about frames, errors and windows. It does not pace the frames: it is there to show that a capture holds what a program needs, not to show it at the speed of the program.

Each API has an executor of its own, registered by its API group: today Direct3D 7 and 8, OpenGL and the Win32 windowing calls (GDI32, User32, WGL), and another API is added with its own. There is no translation of one API to another. The Direct3D 7 executor replays a program in a window, whatever it did: the primary surface shows the window, the back buffer of a flipping chain is a surface of the replay, and a flip is a blit of it to the window. A call the executor has no code for fails the replay, rather than draw something wrong.

Playing more than the plain sequence

A program that needs more (a frame played twice, the frames at the pace of the dumped process) links ReplayEngineCore and plugs into it, without the engine knowing what it is for:

InterfaceUse
IFrameExecutorPlays the calls of one frame. It reads them from the IFrameHost (the engine), may keep them, and executes them through the host, in any order and any number of times. The engine presents the frame and pauses between two frames. SequentialFrameExecutor is the default: each call is executed as it is read. An executor can wrap another (it is given a host that waits when the call which ends a frame is read, for instance).
ICallExecutorReplays the calls of an API. ReplayEngine::add_call_executor replaces the one of an API. It can read and write the back buffer, save and put back the state of the device, and tell when a call is executed if its frame is played again (get_execution_class).
Hooks of D3D7CallExecutorA class that derives from it can make an object twice, or use another object than the one the replay made: after_call, take_object, resolve_object, on_object_registered, on_object_released, on_object_gone and on_reset, with run_handler and release_object_reference to work with.
ICallInterceptorSees every call before and after it is replayed, and may skip it.
