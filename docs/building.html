API Interceptor Overview Capture Components Building

Building & testing

CMake, MSVC, C++14. Two builds (32-bit and 64-bit) are needed because the programs that are studied are often 32-bit, so the injected parts have a build of each.

Build

build.bat                    :: incremental, x86 + x64, outputs in build_final\
build.bat --from-scratch     :: wipe, configure, build
build.bat --debug            :: Debug instead of Release

Third-party code is in deps/ (Detours, Dear ImGui, googletest, Zstd; the Khronos headers of OpenGL). The project can also be built as a subproject of another one: see Used by another project.

The collected build

build_final\ is what a release is, so that it can be zipped as it is and unpacked anywhere. build.bat empties it at the start of its collecting step, so nothing of an earlier build or of the other configuration stays in it, and then installs both build trees into it (cmake --install with --prefix build_final, once for build_x86 and once for build_x64):

  • tools\APIDumper\: the dumper and its DLL, of both architectures, and the printer of a capture;
  • tools\Replay\: the replay engine and the replay player, of both architectures.

Where a program has both architectures, the 64-bit one has the suffix _x64 and the 32-bit one _x86. A program looks for the ones it starts or loads next to itself (the dumper for its DLL, the 64-bit replay player for its 32-bit pair), which is why a group is installed as a whole. What goes where, and under which name, is written in cmake/install.cmake, as an install rule for each program. Only the programs named there are installed, so a program that is not a target any more (after a rename, say) cannot end up in build_final, and a program that is missing makes the install fail instead of leaving a hole.

Nothing else is installed: no libraries and no debug information. A Release build writes no .pdb files at all; a Debug build writes them next to its programs in the build tree, and they are not installed. The installing needs CMake 3.15 or newer (cmake --install).

Test data is in src/tests/data and is not collected.

Source layout

Public headers are in include/ and sources in src/; both have the same groups, and a module is include/<Group>/<Module> and src/<Group>/<Module>. An include names the group: #include "interception/hooks/D3D8/types.h". The namespaces follow the same path: a class of the D3D8 module is Interception::Hooks::D3D8::Foo, one of the replay engine is Replay::ReplayEngineDLL::Foo. The exceptions are Common, whose namespace is APIInterceptor, and the tests, in Tests. The two utility modules of the interceptor core have namespaces of their own, Interception::Core::D3D8Utils and Interception::Core::OpenGLUtils.

GroupModules
interception/hooksD3D8, GDI32, HooksCommon, Kernel32, OpenGL, User32, WGL

ReplayReplayEngineCore, ReplayEngineDLL, ReplayPlayer, ReplayPlayerSupport

Programs have sources only; the third-party Khronos headers are in deps/Khronos.

CMake layout

The root CMakeLists.txt holds the options and the settings every project shares, then includes one file per group from cmake/, in this order: interception.cmake (hooks and the interceptor core), libraries.cmake (the loader of workloads and the launcher of an injected program), tools.cmake (the dumper and the printer), usage.cmake (what a project which builds on this one needs to compile against it), tests.cmake, install.cmake (what the release holds, with the helpers of install_helpers.cmake) and folders.cmake (the folders of the solution, with the helpers of folder_helpers.cmake). The order matters: the files share variables, and a target must exist before it is given a folder.

Solution layout

The generated Visual Studio solution groups projects in folders: Interception (Hooks, Core), Capture, Tests, Third party. File lists are globbed with CONFIGURE_DEPENDS, so a new file is picked up by the next build.

Tests

One test program, APIInterceptorTests, with googletest. Shared helpers (Tests::Fixtures) live in src/tests/fixtures.*, which are a library of their own, APIInterceptorTestSupport, so that a project which builds on this one can use them.

Used by another project

The libraries can be built by a project that has this one as a submodule (add_subdirectory(deps/APIInterceptor EXCLUDE_FROM_ALL), with the APIINTERCEPTOR_BUILD_* options set before it). Each library carries the include directories it needs (usage.cmake), so the project includes headers by the same names; install.cmake does nothing then, since the project has a release of its own. The script build.bat takes --source-dir <dir>, and builds and collects that project instead. The test support and googletest are available to its tests when APIINTERCEPTOR_BUILD_TESTS is on.

Installed package

The static libraries can also be installed and found by find_package(APIInterceptor):

cmake --install <build dir> --config Release --component Development --prefix <prefix>

The package exports APIInterceptor::APIDumpLoader, APIInterceptor::D3D8Utils, APIInterceptor::InjectionLauncher (and the Detours and Zstd libraries they use), with their headers. The hooks themselves (the APIInterceptor object library) are built through add_subdirectory, since a DLL that is injected has to contain them.

Code conventions

  • There are no anonymous namespaces: helpers of a class are private static members, helpers of a test file are file-scope static functions, and test doubles that more than one test file needs are in src/tests/test_doubles.*.
  • Everything is in a named namespace; definitions are written qualified (Ret NS::f()) rather than inside namespace blocks.
  • Names: _ptr for pointers, _vec, _set, _map for containers, _func for callables, _f32mat for matrices, _fp32vecN / _u8vecN for fixed arrays; constants are constexpr UPPER_CASE.
  • Functions, members, variables and struct fields are in alphabetical order. Static create_ptr() is the first function declared in a class header.
  • One return per function (goto end for early exits), one action and one condition per line in if, == false rather than !, else and if on separate lines, mutex locks in their own block.
  • A function call that is one of several conditions of an if is made before it, into a variable, and the ifs are nested in the order the conditions were evaluated, so that a call is made only when the conditions before it hold. Accessors, getters and lookups (size(), at(), empty(), find()) stay in the condition.
  • Consecutive statements are aligned in runs: the =, the opening parenthesis of each call (reader.read_u64 (); under reader.read_bool();), and in a condition the && column, the comparison operators and their right operands. A blank line starts a new run, so one long declaration does not widen the others.
  • A list or an expression that gets long (about 140 columns) is broken with one element or operand per line, not wrapped at the margin.
  • A default of a switch that means "this value is not supported yet" calls AI_FAIL_UNSUPPORTED(value), which ends the process in every build.
  • Comments say why or state a contract; they are short.
